# VICI Tech Assignment — LLM Gateway + Browser Automation Agent
This document is the authoritative spec for this repository. It defines architecture, coding standards, safety boundaries, testing rules, and execution constraints. Follow this strictly.

---

## 0. Mission

Build a production-style system that combines:
- LLM Gateway (LiteLLM-style, OpenAI-compatible)
- Browser Automation Agent (Playwright)

The system must be runnable end-to-end, produce verifiable artifacts, include structured logs, enforce safety boundaries, be modular and extensible, and pass tests at every stage.

Do NOT skip structure. Do NOT hardcode hacks. Do NOT add features beyond scope.

---

## 1. Architecture

Frontend (React + TSX)
        ↓
FastAPI Backend
   ├── LLM Gateway
   └── Agent Runner
           ↓
    Playwright Agent
           ↓
Artifacts + Logs

## 2. Technology Stack (MANDATORY)

- Backend: Python 3.11+, FastAPI, Pydantic, Uvicorn, Pytest, JSON structured logging
- Agent: Playwright (Python), HTML→PDF via Playwright print or python-pptx, deterministic dry-run
- Frontend: React + TypeScript (TSX), clean layout, minimal CSS
- Containerization: Docker, docker-compose, Makefile

---

## 3. Repository Layout (REQUIRED)

- backend/app: FastAPI app, routers, providers, middleware, models
- backend/tests: pytest tests for gateway and agent runner
- agent.py: Standalone agent CLI and workflow
- frontend/: React app (Vite-style) with required components
- runs/: Per-run artifacts served by backend
- outputs/ and run_logs/: Generated by agent inside per-run directories

## 4. LLM Gateway

### 4.1 Endpoints
- GET /health → returns status, version, timestamp
- POST /v1/chat/completions → OpenAI-compatible minimal schema
  - Generate request_id (UUID)
  - Measure latency
  - Include provider metadata
  - Return usage structure (even if mocked)

### 4.2 Provider Abstraction
- Interface: generate(messages, temperature, max_tokens) → text, usage, meta
- Providers: claude_cli.py, openai.py, mock.py (all implement the same interface)
- Router may NOT call providers directly; route through abstraction layer

### 4.3 Observability
- Log every request as JSON lines including: request_id, route, provider, model, latency_ms, retry_count, error (if any)

### 4.4 Safety Boundaries
- Request size limit
- Timeout per request
- Concurrency limit
- Provider allowlist
- Model allowlist
- Retry limit (max 2 retries)
- Never allow unlimited retries or unbounded input

---

## 5. Agent

### 5.1 CLI
- Run: python agent.py --ticker AAPL --source URL --gateway URL

### 5.2 Workflow
1. Launch browser (headless)
2. Navigate to source URL
3. Extract main content
4. Save screenshots
5. Save trace.zip
6. Call Gateway endpoint
7. Generate: report.md and slides.pdf
8. Save structured run.json

### 5.3 Logs
- run_logs must include: run.json, trace.zip, screenshots/, request_ids used
- run.json must include: ticker, source, steps, timings, artifacts, model used, latency summary

## 10. Coding Standards

- No global variables; use dependency injection where appropriate
- No hardcoded API keys; config via env variables
- Pydantic models for API schemas
- Structured JSON logging for observability
- Type hints everywhere

---

## 11. Execution Rules

Order of work:
1) Backend skeleton → 2) Add tests → 3) Keep gateway working → 4) Build agent → 5) Build frontend

Definition of Done per phase:
- Code runs without error; Tests pass; Logs generated; Clear output files exist

---

## 12. Performance Mindset

- Minimize latency; avoid blocking calls; keep code modular
- Ensure reproducibility and deterministic dry-run mode
- Provide full traceability

---

## 13. Prohibited

- Giant monolithic files; skipping abstraction layer; mixing UI and backend logic
- Unbounded input handling; silent failures; hidden side effects

---

## 14. Final Goal

Deliver an engineering-grade LLM Gateway + Browser Agent system demonstrating:
- Provider abstraction, Observability, Safety boundaries, Verifiable artifacts, Reproducible runs, Full-stack integration
